# @service/product — RFC implementation

Новое приложение сервиса управления товарами. Предыдущая реализация сохранена
в `../_service` как reference и не является источником целевых бизнес-правил.

Источник принятых решений: workspace `agent/docs/rfc-product-constructor.md`.
Область реализации и проверки: `../REWRITE-CONTRACT.md`.

- Следовать ООП и соглашениям NestJS старого сервиса: DTO-классы,
  `class-validator`/`class-transformer`, injectable services и регистрация через
  modules. Не заменять DTO ручными проверками типов и собственными парсерами.
- Транспортные DTO принадлежат `controller/dto`, один контракт на файл. Сервисы
  и репозитории не импортируют DTO; controller переводит их в команды приложения.
- Только каталог: примитивы, типы, товары, варианты, значения и связи изображений.
- Категории, склад, учет, цены, резервы и заказы принадлежат другим сервисам.
- Property, PropertyOption, Unit и Brand идентифицируются ручными кодами.
  ProductType, Product и Variant используют UUID; Image сохраняет UUID внешнего
  файла. Не добавлять Product/Variant дополнительный `code`.
- Product/Variant никогда не удаляются: active/archived, редактирование архива
  разрешено; состояние родителя не переписывает личные состояния вариантов.
- Изображения товара связаны с Variant; Image — проекция файла, не байты/URL.
- Изображение бренда принадлежит бренду. При замене или очистке изображения
  новые связи, удаление старой проекции и событие `brand.images.removed`
  записываются одной транзакцией. Payload содержит `imageUuids`; File service
  удаляет старые объекты асинхронно. Сохранение того же UUID не вызывает удаления.
- Required/multiple задаются полем типа; Property определяет вид значения и единицу.
- При удалении поля типа назначения и значения удаляются каскадно.
- Создание Product с минимум одним Variant атомарно; PATCH явный, omission не archive.
- Команды проверяют актуальность сущности и структуры типа; Variant mutations
  не должны обходить проверку версии товарного агрегата.
- `synchronize: false`; изменения схемы только явными миграциями. Старую БД
  и очереди нового несовместимого контракта нельзя переключать неявно.
- Опции принадлежат Property типа OPTIONS. Не добавлять отдельный справочник
  списков и не вводить удаление используемой опции без нового решения RFC.
- Общая outbox-инфраструктура принадлежит `../library/sellgar.outbox.library`;
  расширение ее контракта требует согласованной области задачи.
- Входящие интеграционные события проходят через `InboxModule`; запись inbox и
  изменение локальной проекции выполняются одной транзакцией. Исходящие события
  агрегата записываются через `ProductOutboxModule` в его доменной транзакции.
- Проверять реальные бизнес-правила, транзакции, FK и негативные сценарии;
  успешная сборка сама по себе не подтверждает поведение БД.

Проверки из корня репозитория: `yarn build:product_srv`.
Из `service`: `yarn test --runInBand`.
